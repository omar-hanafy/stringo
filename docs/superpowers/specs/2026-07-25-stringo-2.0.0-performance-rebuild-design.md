# stringo 2.0.0 - performance rebuild

**Date:** 2026-07-25
**Status:** approved for planning
**Scope:** stringo only. `dart_helper_utils` follow-up is separate work.

## 1. Why

A performance audit of stringo 1.0.0 found that the package is not slow because
of the algorithms it chose. It is slow because it repeats work: it recompiles
regexes inside loops, and it allocates whole-string copies to answer questions
that need one character.

All figures below are measured on this machine (Dart VM, `dart run`, warmed,
Darwin arm64). They are reproducible via the benchmark suite this spec adds.

### 1.1 The defect that matters most

```dart
bool get isEmptyOrNull => this == null || this!.clean.isEmpty;
```

`clean` is `replaceAll('\n','')` followed by `replaceAll(RegExp(r'\s+'),'')`.
So a blank check allocates two full copies of the string and compiles a regex,
then asks whether the result is empty.

| `isBlank` on a non-blank string | measured |
| --- | --- |
| 10 chars | 510 ns |
| 1,000 chars | 30,905 ns |
| 100,000 chars | **3,041,429 ns (3.04 ms)** |

The cost is linear in length for a question that is answerable in constant time.
A single blank check on a 100 KB payload costs 3 ms. A scan that returns at the
first non-whitespace code unit measures **2.5 ns**.

This compounds: `capitalizeFirstLetter`, `lowercaseFirstLetter`, and
`capitalizeFirstLowerRest` each call `isBlank`, and every case conversion calls
those once per word. `'hello world'.toPascalCase` compiles roughly 11 regexes.

### 1.2 Full audit

| Operation | 1.0.0 | Prototype | Gain |
| --- | --- | --- | --- |
| `isBlank` (100k chars) | 3,041,429 ns | 2.5 ns | ~1,000,000x |
| `toWords` | 1,960 ns | 136 ns | 14x |
| `toCamelCase` | 3,665 ns | 263 ns | 14x |
| `toSnakeCase` | 2,201 ns | 279 ns | 8x |
| `slugify` (54 chars) | 10,873 ns | 1,068 ns | 10x |
| 200k identifiers to snake_case | 356 ms | 51 ms | 7x |

Three root causes:

1. **Regex recompilation.** Every `RegExp(...)` sits in a getter body, so it is
   reconstructed per call. Dart does not cache by pattern string. `slugify`
   compiles four per call.
2. **Allocation instead of scanning.** `isBlank` is the worst case, but the same
   pattern appears throughout.
3. **Multi-pass pipelines.** `slugify` makes roughly six full passes and six
   allocations. Each case conversion allocates a `List`, N substrings, a joined
   string, and then a cased copy.

## 2. Non-goals

### 2.1 Native code via FFI is rejected, on measurement

The question was raised whether moving the parsing work to Rust or C++ and
calling it through `dart:ffi` would be faster. It would not. A C dylib was built
and measured rather than reasoned about.

| 24-char identifier | ns/op |
| --- | --- |
| FFI round-trip (alloc, encode, call, decode, free) | 164 |
| FFI with pre-allocated reused buffer (best case) | 130 |
| **Dart built-in `toLowerCase()`** | **20** |

FFI is 6.5x slower than staying in Dart at 24 chars, and still 4.8x slower at
100,000 chars (327,970 ns vs 68,053 ns). Bare FFI call overhead with no string
work at all is 9.3 ns, which by itself exceeds the total cost of several
stringo operations.

The cause is structural, not tunable. Dart strings are UTF-16, so crossing the
boundary forces an encode and a copy in each direction. Dart's own string
primitives are already native code inside the VM and do not pay that boundary.
FFI wins when compute per byte is high (compression, crypto, parsing megabytes);
stringo does single-pass character work, which is precisely the profile where
marshalling dominates.

Secondary costs, any one of which would be disqualifying on its own: `dart:ffi`
does not exist on dart2js or dart2wasm, so web support would be lost; prebuilt
binaries would be needed for roughly nine platform/arch combinations, via a
build-hook mechanism that is still experimental; the zero-dependency guarantee
in AGENTS.md would be broken; pana platform points would drop.

**The full 7x to 14x is available in pure Dart. There is no reason to leave the
language.**

### 2.2 Unchanged commitments

- The scope rule in AGENTS.md stands. stringo transforms text; it does not judge
  whether text is a valid instance of a real-world concept. No validators.
- Zero dependencies remains a hard constraint. Only `dart:core` and
  `dart:convert`.
- `slugify` still does not transliterate, and grapheme-cluster segmentation
  still requires `package:characters`. Both stay documented limitations.

## 3. Architecture

Layers, with dependencies pointing strictly downward. No layer knows about the
one above it.

```
lib/
  stringo.dart                    # sole public entry point
  src/
    chars.dart                    # code-unit classification
    word_scanner.dart             # the engine: allocation-free boundary scanner
    case_writer.dart              # fused case-mapping writers over the scanner
    stringo.dart                  # `Stringo`: pure static functional core
    patterns.dart                 # String patterns + precompiled RegExp
    extensions/
      case.dart                   # thin sugar, delegates to Stringo
      transform.dart
      checks.dart
```

### 3.1 The engine

1.0.0 has no engine. Each conversion independently re-splits the input with a
lookbehind regex. The rewrite introduces one tokenizer that everything shares:

```dart
/// Walks word boundaries, invoking [emit] with each (start, end) pair.
/// Allocates nothing.
void scanWords(String s, void Function(int start, int end) emit);
```

Boundary rules, preserved exactly from 1.0.0's regex
`(?<=[a-z])(?=[A-Z])|[_\-\s]+|(?<=[A-Z])(?=[A-Z][a-z])`:

- zero-width split between an ASCII lowercase and an ASCII uppercase
- a consumed run of `_`, `-`, or whitespace
- zero-width split between an ASCII uppercase and an uppercase followed by a
  lowercase, which keeps `HTTPServer` splitting as `HTTP` + `Server`

Whitespace is defined as the ECMAScript `\s` set, matching what the 1.0.0 regex
matched: `\t \n \v \f \r`, space, NBSP, U+1680, U+2000-U+200A, U+2028, U+2029,
U+202F, U+205F, U+3000, U+FEFF. Deviating from this set silently changes
behavior for non-ASCII input, so it is asserted directly in tests.

Because splits are driven by ASCII character classes, non-ASCII letters are
never boundaries and surrogate pairs are never split. `'a😀B'.toWords` stays
`['a😀B']`.

### 3.2 Allocation fusion

Conversions write directly into one `StringBuffer` as the scanner emits
boundaries. No intermediate `List`, no per-word substrings, no separate cased
copy. `toSnakeCase` goes from `2 + N` allocations to exactly one.

### 3.3 ASCII fast path

A single cheap scan establishes whether every code unit is below U+0080. If so,
case mapping is done inline on code units. If not, the conversion falls back to
Dart's native `toLowerCase()` / `toUpperCase()`.

This is mandatory for correctness, not an optimization detail. Dart's casing is
full Unicode: `'ÉCOLE'.toSnakeCase` is `'école'`, and `'straße'.toUpperCase()`
is `'STRASSE'` in some locales. An ASCII-only implementation would silently
corrupt non-English text. The first prototype written for this audit made
exactly that mistake, which is why section 6 does not rely on hand-written
examples.

## 4. Public API

### 4.1 Functional core

`Stringo` is an `abstract final class` used as a namespace: not instantiable,
not extendable, one exported symbol, and it tree-shakes per method.

Every extension member that carries logic becomes a one-line delegation to a
core function, so there is exactly one implementation of each behavior and it is
testable without going through extension resolution. A few members are pure
null-guards over `dart:core` and stay inline rather than gaining a pointless
core function: `orEmpty` (`s ?? ''`), `nullIfEmpty`, `nullIfBlank`,
`tryToLowerCase`, `tryToUpperCase`.

The core also gives any consumer hitting an extension-name collision a complete
escape hatch:

```dart
import 'package:stringo/stringo.dart' show Stringo;
```

Core naming drops the `to` prefix, which reads correctly in call position:

```dart

// case

static String screamingCase(String input);
static String screamingSnakeCase(String input);
static String screamingKebabCase(String input);

static String pascalKebabCase(String input);
static String camelSnakeCase(String input);
static String camelKebabCase(String input);
```

Core functions take non-nullable `String` except where nullability is the point

### 4.2 Extensions

Extension names are unchanged and unprefixed, honoring the existing AGENTS.md
convention: `StringCaseExtensions`, `NullableStringCaseExtensions`,
`StringTransformExtensions`, `NullableStringTransformExtensions`,
`StringChecksExtensions`.

Member names are unchanged from 1.0.0 except for the removals in 4.3. Ergonomics
are identical: `'x'.toSnakeCase`, `'x'.slugify()`, `s.isBlank`.

`toTrainCase` is retained as a one-line alias of `toPascalKebabCase`, which is
the canonical implementation. Per the decision on 2026-07-25, the alias gets a
single delegation assertion rather than a duplicated test suite.

### 4.3 Removals

| Removed | Replacement | Reason |
| --- | --- | --- |
| `isEmptyOrNull` | `isBlank` | exact synonym |
| `isNotEmptyOrNull` | `isNotBlank` | exact synonym |

`isEmptyOrNull` is called by DHU's own source. See section 9.

### 4.4 Additions

Precompiled `RegExp` objects exported alongside the existing `String` patterns,
so consumers can use them without paying compilation:

```dart
const String regexNumeric = r'^\d+$';       // retained
final RegExp patternNumeric = RegExp(regexNumeric);  // new
```

The same for alphanumeric, startsWithNumber, containsDigits, alphabet, and
hasCapitalLetter.

## 5. Behavior changes

These are the eight defects the audit found. Each is a deliberate break
justified by the major version.

| # | Behavior | 1.0.0 | 2.0.0 |
| --- | --- | --- | --- |
| 1 | Leading separator corrupts camelCase | `'_leading'.toCamelCase` is `'Leading'` | `'leading'` |
| 2 | `toWords` emits phantom empty words | `'  a  '.toWords` is `['','a','']` | `['a']` |
| 3 | `slugify` keeps input hyphens when the separator differs | `'a-b'.slugify(separator:'_')` is `'a-b'` | `'a_b'` |
| 4 | `slugify` multi-char separator quantifies only its last char | correct only by luck | correct by construction |
| 5 | `truncate` exceeds its own limit | `'abcdefgh'.truncate(5)` is `'abcde...'` (8 chars) | `'ab...'` (5 chars) |

| 6 | `toCharArray` splits surrogate pairs | `'😀'` is two broken halves | one code point |
| 7 | Null handling is inconsistent | `mask` returns `''`, `truncate` returns `null` | uniform: null in, null out |
| 8 | `''.toWords` | `['']` | `[]` |

Defect 1 is caused by defect 2: a leading separator produces an empty first
word, which shifts the real first word to index 1 where camelCase capitalizes
it. Both disappear with the engine rewrite, since the scanner does not emit
empty words.

Defect 6 is fixed with `String.runes` from `dart:core`, so it costs no
dependency. Grapheme clusters (flag emoji, combining marks) still require
`package:characters` and that limitation stays documented.

### 5.1 Exact rules for the two defects that admit more than one reading

**Defect 3, `slugify` separator handling.** The rule becomes: `-`, `_`, and
whitespace are all *separator-producing* characters. Any run of one or more of
them, in any mix, collapses to a single `separator`. Everything outside
`[a-z0-9]` after lowercasing is dropped. Separators are then trimmed from both
ends. This makes the function independent of which separator was requested,
which is what 1.0.0 got wrong: it special-cased `_` and whitespace but let a
literal `-` through untouched.

**Defect 5, `truncate` length semantics.** The rule becomes:

```
if (input.length <= length) return input;
return input.substring(0, max(0, length - suffix.length)) + suffix;
```

So `length` is the maximum total result length. The one case where the result
may still exceed `length` is `suffix.length > length`, where there is no
shorter answer that keeps the suffix intact; the result is then exactly
`suffix`. The property test in section 6 is stated as
`result.length <= max(length, suffix.length)` for this reason. `length <= 0`
continues to return the empty string.

### 5.2 Explicitly preserved quirks

These looked like bugs, were checked, and are being kept because they are
documented and load-bearing:

- `toWords` does not split on digit boundaries: `'abc123Def'` stays one word.
- `clean` and `toOneLine` join without inserting a separator.
- `toTitleCase` always capitalizes the first word, then honors
  `titleCaseExceptions`, which remains public API.
- `toTitle` preserves `-` and `_` separators rather than normalizing them.

## 6. Testing

Hand-written examples are how defect 1 survived 1.0.0, and how the first
prototype in this audit shipped an ASCII-only casing bug that hand checks
missed. Examples are therefore not the primary mechanism.

**Layer 1: differential fuzz.** A reference implementation encoding 1.0.0
semantics is checked against the new engine over generated input: identifiers,
separator soup, unicode, emoji and surrogate pairs, acronym runs, pathological
whitespace, empty and single-character strings. Each of the eight intentional
changes in section 5 is registered as a named exception in the harness, so any
*unregistered* divergence fails the build. This is what proves the engine.

**Layer 2: property tests.** Invariants rather than examples:

- `slugify` is idempotent: `slugify(slugify(x)) == slugify(x)`
- `snakeCase -> camelCase -> snakeCase` round-trips for identifier-shaped input
- `words` never emits an empty element
- `truncate(n).length <= max(n, suffix.length)` for all n
- ASCII input always produces ASCII output from every casing conversion, which
  is the invariant the fast path in 3.3 depends on. The converse does not hold
  and is not asserted: some non-ASCII characters case-map into ASCII, for
  example the Kelvin sign U+212A lowercasing to `k`.

**Layer 3: performance-contract tests.** These assert algorithmic behavior, not
wall-clock timings, so they cannot flake on noisy CI runners:

- `isBlank` on a 10-char string and a 10-MB string must cost within a small
  constant factor of each other. This test fails against 1.0.0 and is the
  permanent guard against defect 1.1 returning.
- No `RegExp` is constructed inside any function body. Enforced by a source
  scan over `lib/`, so the regex policy cannot silently erode.

## 7. Regex policy

Rule: **no `RegExp` construction inside a function body.**

- The package's patterns become lazily-initialized top-level `final RegExp`,
  compiled once per isolate.
- Hot predicates bypass `hasMatch` and use those objects directly.
- `hasMatch(String pattern, {flags})` keeps its 1.0.0 signature, because DHU
  calls it and because changing the parameter to `Pattern` would silently turn
  regex matching into literal substring matching (`String` implements
  `Pattern`). It is documented as compiling on every call, with a note to hoist
  the `RegExp` in hot loops.

A compiled-regex cache was considered and rejected: it is global mutable state
with unbounded growth, and precompiling the package's own patterns captures the
entire realistic win without it.

## 8. Benchmarks

A `benchmark/` directory, excluded from the pub archive via `.pubignore`,
containing a runnable suite covering the operations in section 1.2 plus the
200k-identifier server workload. It reports ns/op and is for humans; CI
correctness is owned by the layer-3 tests in section 6, not by timings.

## 9. Constraints and follow-up

**DHU coordination.** `dart_helper_utils` pins `stringo: ^1.0.0`
(`>=1.0.0 <2.0.0`), so it cannot resolve 2.0.0 until it is bumped. Verified
against DHU's `pubspec.yaml`, its `pubspec.lock` (pinned at stringo 1.0.0), and
the absence of any `dependency_overrides`. Existing DHU users therefore cannot
be broken by this release.

Verified breakage inventory for the eventual DHU major, all in one file,
`lib/src/extensions/string_extensions/general_string_extensions.dart`:

- **Seven compile errors**, not three as originally estimated here: six uses of
  `isEmptyOrNull` (lines 143, 173, 205, 242, 246, 266) and one of
  `isNotEmptyOrNull` (line 238). The rename to `isBlank`/`isNotBlank` is
  value-preserving, since 1.0.0's `isEmptyOrNull` was true exactly when every
  code unit matched `\s`, which is what the 2.0.0 scan tests.
- **No behavior changes reach DHU's `lib/`.** DHU calls none of `toWords`,
  `truncate`, `toCharArray`, `slugify`, `mask`, or `insert`. The
  `String` to `String?` return-type changes on `mask` and `insert` cost DHU
  nothing.
- `hasMatch`, `tryToLowerCase`, and `clean` are unchanged in signature and
  result, so their eight call sites survive untouched.
- After the seven-identifier rename, `dart analyze` over DHU is clean: no
  second-order breakage. Three DHU *tests* still fail, all from the `truncate`
  change (`test/public_api_exports_test.dart:22`,
  `test/string_extension_test.dart:7` and `:12`).

**Open decision for the DHU major, not for this release.** `isEmptyOrNull` and
`isNotEmptyOrNull` on `String?` are part of DHU's public surface through the
re-export. Removing them here removes them from DHU's API for `String?` while
DHU keeps them on `Map?`, `Iterable?`, and `List?`, which is an inconsistency
DHU users will notice. Because stringo no longer defines those names, DHU may
re-declare them on `String?` in its own extensions with no partition violation,
if softening the break is preferred.

**Partition constraint.** A member name must exist in exactly one of stringo and
DHU. 2.0.0 adds exactly seven top-level symbols: `Stringo` and the six
precompiled `pattern*` objects. Verified absent from DHU's `lib/`, and also from
`collection` and `convert_object`, which DHU re-exports alongside stringo (an
ambiguous export is a compile error at the export directive, so grepping DHU
alone would have been insufficient). Confirmed at compile level: a probe
importing only `package:dart_helper_utils/dart_helper_utils.dart` and binding
all seven names analyzes clean.

The extension member set strictly shrinks in this release, so a new
extension-member collision is structurally impossible rather than merely
absent.

**Pana.** The 1.0.0 baseline is 160/160 and CI requires a perfect score. Every
new public member needs a doc comment; formatting and the dry-run stay clean.

## 10. Deliverables and sequencing

Engine first, verified against 1.0.0, before anything downstream is written.
Documentation written against an API that is still settling has to be written
twice.

1. `chars.dart`, `word_scanner.dart`, `case_writer.dart` plus the layer-1 and
   layer-2 test suites. Gate: differential fuzz is green.
2. `Stringo` core, `patterns.dart`, extensions rewritten as delegations. Gate:
   full test suite green, `dart analyze` clean, pana still 160/160.
3. Benchmark suite. Gate: measured gains match section 1.2 within noise.
4. README rewritten from scratch.
5. AI plugin: `use-stringo` skill updated to the new API, new v1-to-v2 migration
   skill, both plugin manifests version-bumped to 2.0.0, and
   `tool/validate_agent_plugin.dart` passing.
6. `CHANGELOG.md` 2.0.0 entry with the section 5 migration table, and AGENTS.md
   updated to describe the new tree, the regex policy, and the removals.

## 11. Assumptions

Stated so they can be corrected rather than discovered late:

1. `toTrainCase` survives as an alias of the canonical `toPascalKebabCase`,
   tested only by a single delegation assertion.
2. Defect 7 resolves toward "null in, null out". The consequence is a signature
   change, not just a value change: `NullableStringTransformExtensions.mask`
   returns `String?` instead of `String`, and yields `null` rather than `''` for
   a null receiver. Callers relying on the non-nullable return will see a
   compile error, which is the desired outcome for a major version.
3. The four members DHU calls that are *not* being removed keep their exact
   1.0.0 signatures, so the DHU follow-up stays mechanical.
4. No new public member introduces a name DHU already defines. Verified before
   release, per section 9.
